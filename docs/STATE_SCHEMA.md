# `state.json` schema

Everything the Django app shows comes from one published JSON file
(`state.json`), fetched by `timing/services.py` and never generated by
Django itself. That split is deliberate: **any script that writes a
JSON object matching this document is a valid drop-in data source** --
you don't need to touch `timing/`, `poller.py`, or `replay.py` to plug
in a new one. This file is that contract.

Today there are two producers, both invoked from `poller.py`:

| Source | Module | When it's used |
|---|---|---|
| F1's own live timing feed | `poller.py` | Whenever F1's feed reports a session in progress. |
| OpenF1 replay | `replay.py` | Fallback, whenever F1's feed reports no session in progress. Replays the most recently completed session from [OpenF1](https://openf1.org)'s free API so the dashboard has real data to show/test against between sessions. |

A third source -- a custom race, a simulation, a recorded test session,
anything -- just needs its own script that writes a file matching this
schema to the same path. See "Writing your own source" at the bottom.

## Top-level shape

```jsonc
{
  "ok": true,
  "mode": "live",              // "live" | "replay" -- see "mode" below
  "generated_at": "2026-03-01T14:32:07.123456+00:00",  // added by poller.py's main(), not by build_state()
  "reason": null,              // present (string) only when ok=false

  "session": { ... },
  "meeting": { ... },
  "drivers": { ... },
  "positions": { ... },
  "intervals": { ... },
  "laps": { ... },
  "best_laps": { ... },
  "stints": { ... },
  "pits": [ ... ],
  "race_control": [ ... ],
  "weather": { ... } | null,
  "track": { "outline": [...], "cars": {...} },

  "replay": { ... } | absent   // only present when mode == "replay"
}
```

`ok` / `reason` / `generated_at` are the only fields every producer is
required to always include, even on failure. Everything else may be
missing, empty, or `null` when that particular piece of data isn't
available -- every consumer in `timing/services.py` already treats a
missing key as "no data" rather than an error. **When `ok` is `false`,
`poller.py`'s `main()` merges onto the previously-published file** (see
`build_state()` / `main()` in `poller.py`) so a single bad tick shows
slightly-stale data instead of blanking the dashboard; a new source
doesn't need to reimplement that, it only needs to return
`{"ok": false, "reason": "..."}` on failure and the merge happens
around it.

### `mode`

`"live"` or `"replay"`. Purely informational -- `timing/services.py`
doesn't branch on it, but `timing/views.api_status` passes it through
and the dashboard header uses it to show a small "REPLAY" badge (see
`get_data_freshness()` in `timing/services.py` and the `pollStatus()`
JS in `timing/templates/timing/dashboard.html`). A new source can use
any string it likes here (e.g. `"simulation"`) -- the badge just won't
know how to label it. It's fine to always write `"live"` if your
source has no notion of "this is a replay".

### `session`

```jsonc
{
  "session_key": "any string/number, opaque",
  "meeting_key": "any string/number, opaque",
  "session_name": "Race",       // shown in the dashboard header
  "session_type": "Race"        // not currently rendered, kept for future use
}
```

`session_key` / `meeting_key` are passed around by `timing/views.py`
and `timing/services.py` but never parsed -- they're opaque handles.
The live source uses F1's session path string; the replay source uses
`"openf1:<session_key>"`. Use whatever's convenient; just be
consistent within one producer so nothing looks like it changed
sessions when it hasn't.

### `meeting`

```jsonc
{
  "meeting_name": "Bahrain Grand Prix",
  "circuit_short_name": "Bahrain",   // must match a key in circuits.py for the rain radar map to center correctly
  "latitude": 26.0325,               // decimal degrees, or null
  "longitude": 50.5106
}
```

If `circuit_short_name` matches an entry in `circuits.py`'s
`CIRCUIT_COORDINATES`, both live and replay sources look up
`latitude`/`longitude` from there automatically. Add missing circuits
to that one shared table rather than hardcoding coordinates in a new
source.

### `drivers`

Dict keyed by **driver number as a string** (`"1"`, `"44"`, ...):

```jsonc
{
  "1": {
    "name_acronym": "VER",
    "full_name": "Max Verstappen",
    "team_name": "Red Bull Racing",
    "team_colour": "3671C6",     // hex, NO leading "#" -- the template adds it
    "headshot_url": "https://..."  // or null
  }
}
```

### `positions`

Dict keyed by driver number (string) -> current race position (int):

```jsonc
{ "1": 1, "44": 2 }
```

### `intervals`

Dict keyed by driver number (string):

```jsonc
{
  "44": { "gap_to_leader": 3.4, "interval": 0.8 }
}
```

Both values are normally a float (seconds) but may be a string like
`"+1 LAP"` for a lapped car -- the dashboard's `fmtGap()` handles
either. `gap_to_leader` for the leader themself is typically `0` or
absent.

### `laps`

Dict keyed by driver number (string), each driver's most recent lap:

```jsonc
{ "1": { "lap_duration": 91.234, "lap_number": 12 } }
```

`lap_duration` is seconds (float) or `null` for an in-progress/unknown
lap.

### `best_laps`

Dict keyed by driver number (string) -> that driver's fastest
`lap_duration` **so far this session** (float, seconds). This has to
be tracked across the whole session, not just the latest lap, since
neither the live feed nor OpenF1 hands you "personal best" directly --
see how each producer accumulates it (a local cache for the live
source, a full scan of that driver's laps up to the current replay
time for the replay source).

### `stints`

Dict keyed by driver number (string), current tyre only (not full
stint history -- that's covered by `pits` below):

```jsonc
{ "1": { "compound": "MEDIUM", "tyre_age": 8, "stint_number": 2 } }
```

`compound` is one of `SOFT` / `MEDIUM` / `HARD` / `INTERMEDIATE` /
`WET` (or `null`). `tyre_age` is laps on the current set.

### `pits`

List (most recent first, capped to 20), one entry per pit stop so far:

```jsonc
[
  {
    "driver_number": 44,          // int, not string, here
    "lap_number": 14,
    "compound": "HARD",           // tyre fitted, or null if unknown
    "lane_duration": 22.5,        // seconds in the pit lane, or null
    "stop_duration": null         // stationary time only, or null -- rarely available
  }
]
```

Neither producer currently fills in every field: the live source has
no reliable `lane_duration`/`stop_duration` (see the long comment in
`poller.py` about F1's pit-timing feed) but does infer `compound` from
tyre-stint changes; the replay source has `lane_duration` from
OpenF1's `pit_duration` field but no `compound` (OpenF1's `pit`
endpoint doesn't include it). A source with better pit data should
fill in all four.

### `race_control`

List (most recent first, capped to 20):

```jsonc
[
  {
    "date": "2026-03-01T14:32:00+00:00",  // ISO 8601
    "message": "YELLOW FLAG SECTOR 3",
    "flag": "YELLOW",
    "category": "Flag",
    "lap_number": 12
  }
]
```

### `weather`

A single object (not a history) representing current conditions, or
`null` if unavailable:

```jsonc
{
  "air_temperature": 28.4,
  "track_temperature": 41.2,
  "humidity": 38.0,
  "wind_speed": 1.9,
  "wind_direction": 210.0,
  "rainfall": false
}
```

### `track`

```jsonc
{
  "outline": [[x, y], [x, y], ...],   // sampled points tracing the circuit shape
  "cars": {
    "1": { "x": 1234.5, "y": -678.9, "status": "OnTrack" }
  }
}
```

Coordinates are in whatever unit the source's raw feed uses (F1's live
feed and OpenF1's `location` endpoint happen to agree on the same
rough units, but nothing downstream assumes a specific scale --
`timing/templates/timing/dashboard.html` fits the SVG viewBox to
whatever range of points it's given). This whole block is optional and
best-effort in both existing producers -- omit it entirely, or leave
`outline` empty and `cars` `{}`, if a new source has no position feed
to draw from. `status` is never rendered today; pass `null` if you
don't have it.

### `replay` (replay sources only)

Present only when `mode == "replay"`. Purely descriptive -- nothing in
`timing/` reads its fields yet except the dashboard's progress badge:

```jsonc
{
  "source": "openf1",
  "session_key": 9165,
  "virtual_time": "2026-03-01T15:04:30+00:00",  // how far into the replayed session this tick has reached
  "session_progress": 0.42,                     // 0.0-1.0
  "loop_count": 0,                               // increments each time the replay reaches the end and restarts
  "note": "Historical data from OpenF1, replayed for testing/demo purposes -- not a live session."
}
```

A simulation source could reuse this same shape (e.g. `"source":
"simulation"`) or omit it -- it only matters if you want the replay
badge/progress text to show something meaningful.

## Writing your own source

1. Write a script (any language) that produces one JSON object matching
   this document and writes it to the path your Django app's
   `GITHUB_STATE_URL` setting points at (or, for local testing, straight
   into `site/state.json` next to `poller.py`).
2. Fill in only the sections you have real data for; leave the rest as
   empty dicts/lists or `null`. Nothing downstream will crash on a
   missing section -- see the "may be missing" note under "Top-level
   shape".
3. If it's meant to run continuously (a custom race replay, a live
   simulation), model it on the existing loop in
   `.github/workflows/poll.yml`: write the file, commit, push to
   `gh-pages`, sleep, repeat. There's nothing Action-specific about the
   schema itself, though -- a source that just runs on your laptop and
   writes straight into the Django app's expected location works too,
   you'd just skip `GITHUB_STATE_URL` and point `timing/services.py` at
   a local file instead (see `_fetch_state()` in `timing/services.py`
   if you want a `file://`-style variant of that function).
4. Pick a `mode` string that describes what it is (`"live"`,
   `"replay"`, `"simulation"`, your call) and set `ok`/`reason`
   honestly on failure -- that's the only part of the contract that's
   actually load-bearing, everything else degrades gracefully.
